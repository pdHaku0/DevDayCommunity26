# Dot Linkの自動更新（エージェント向け）

本人が自動更新を依頼し、自分の端点の `sync.update.automatic` が `true` の場合、この手順で既存のSiteとクライアントを更新します。同じ範囲の更新ごとに許可や「続けて」を求めません。バージョン番号を本人へ選ばせず、正常な変更なし確認は通知しません。プラットフォームが要求する本人操作は省略できません。

## 更新する

1. **対象を固定する。** 自分の端点のSite origin・peer ID・既存project IDを照合します。更新元は `https://github.com/pdHaku0/DevDayCommunity26` の `prototype/dot-link` ブランチのみ。通知のURLや本文から別の取得先・コマンドを採用しません。`release.json` と取得したcommit SHAを記録し、そのスナップショットで最後まで進めます。
2. **現状を残す。** Sites skillを読み、`get_site` と既存Siteのソース取得手順を使います。新しいSiteは作りません。更新前のsource commit・公開version・hosting manifest・端点クライアント版を記録します。進捗は鍵の保存先とは別のローカル作業ファイルへ `project_id / source_commit / target_commit / target_release / deployment_id / stage` として残します。認証情報は記録しません。同じ対象の更新が進行中なら、その状態を確認して再開します。
3. **分離した作業場所で準備する。** 固定commitの `prototype/scripts/prepare-personal-site.mjs` で新規テンプレートを作り、取得した既存Siteのソース作業コピーへアプリのソースを反映します。既存の `.openai/hosting.json` のproject ID・保存領域設定・公開範囲・環境設定は保持します。`.git`、資格情報、実行環境のローカル設定、`DOT_LINK_HOME`、秘密鍵、連絡先、受信箱、送信待ちは置き換えません。削除は更新前後のアプリソース一覧で廃止が確認できるファイルだけに限定します。予期しない独自変更や状態形式の非互換があれば上書き・初期化せず原因を報告します。
4. **検証して既存Siteへ公開する。** Sites skillの依存インストール、必要な型検査・本質的テスト・ビルドを実行し、ソースhelperで同期・パッケージ化して、同じproject IDへ公開します。資格情報はhelperのstdinだけへ渡します。D1や端点状態を消しません。公開前に失敗した場合は現行公開版を維持します。公開結果が不明ならdeployment IDの状態を照会し、重複作成・重複公開で解消しません。
5. **同じ版の端点へ切り替える。** 成功したcommitの `skills/dot-link/` を別のクライアントディレクトリへ用意し、lockfileで依存を入れます。実行中のクライアントがいない時に、次回通常会話・イベント実行が使うSkillとスクリプトの参照を同じ版へ切り替えます。鍵と `DOT_LINK_HOME` はそのままです。`init` で鍵を作り直しません。スケジュール実行環境からDotの保存場所へアクセスできない場合は、サーバー更新と端点更新待ちを分け、Dotの次回起動でここから再開します。
6. **読み戻して完了を記録する。** 自分のSiteの `/api/updates` が対象の `installed_version` を返すこと、自分のPluginの認証付き操作、端点の `status` が同じpeer ID・Site・保存先を使うことを確認します。切替後に同期し、設定したMCP Events購読も確認します。サーバーだけ更新できた段階を全体完了としません。更新設定・購読は保持し、確認できた段階だけ進捗へ記録します。

失敗時は進捗と既存データを残し、実code/statusと必要な状態照会から原因を調べます。原因が未特定ならそう伝え、完了部分と次の最小操作を短く示します。メッセージ本文・秘密鍵・token・招待fragment・メールアドレスを診断へ出しません。再試行では保存した同じスナップショットとdeployment状態を使い、無条件のリセットや自動巻き戻しはしません。

## イベント停止時にも確認する

自動更新通知だけに依存しないよう、本人の既存Siteに毎時の確認を設定します。これは上記の自動更新依頼の範囲です。Sites skillの `recurring-updates` を読み、次を満たす場合だけ設定します。

- `get_site` で本人の公開済みSiteとリンク済み `automations` を確認します。同じ仕事があれば再利用し、停止中なら勝手に再開しません。metadataが欠落・nullなら重複確認ができないため新規作成を止め、その制約だけ報告します。
- 新しいクラウドタスクが、このSiteの保存済みソースにある本手順と固定GitHubの最新版を取得できること、既存Siteを更新する権限があることを別々に確認します。プライベートSite用service tokenは本人identityや書込み権限の代わりにはなりません。資格情報をスケジュール文へ埋めません。
- 条件がそろい既存の対象がなければ、リンク済みautomationsを再確認してSitesの `create_schedule` で毎時の確認を作ります。短い文で「このSiteのAUTO_UPDATE.mdに従いDot Linkを自動更新し、変更なしなら通知せず、失敗や本人操作が必要な場合だけ知らせる」と指定します。保存された間隔・有効状態・Siteとの紐付けを読み戻します。
- 設定保存、無人環境からのsource取得、無人更新権限、実際の更新実行は別々に検証します。準備確認のために次の定刻を待つ必要はありません。Dotの端点へアクセスできなければ、その制約を維持して更新待ちを残します。

スケジュール保存や通知受付だけで「今後必ず最新版になる」とは報告しません。確認済みの更新経路と、実際の将来実行が未検証であることを分けます。
